# 新需求开发 AI Native 总流程蓝图

## 适用范围

本文基于 `raw/` 中第 1 组“总流程蓝图”材料整理，面向没有明显存量包袱的新需求开发场景。目标不是复述案例，而是提炼一套研发团队可以执行的 AI Native 开发流程。

参考材料：

- `当整个团队开始 0 人工Coding：一份万字AI Native研发实战手册.md`
- `从Vibe Coding到Agentic Engineering：重构后台开发全流程.md`
- `认知重建之后，步入Agentic Engineering的工程革命.md`

## 核心结论

最佳实践不是直接让 AI 从需求生成代码，而是把新需求开发变成一条有阶段、有产物、有门禁、有知识沉淀的工程流水线。

Harness Engineering 不是一个岗位或某个人，而是一套工程思想和流程设计：通过上下文、规范、工具、门禁、反馈回路和知识沉淀，构建让 AI Agent 稳定参与研发的工程系统。

## 标准流程

建议新需求开发采用 9 个阶段：

| 阶段 | 目标 | 关键产物 | 人负责 | AI / Agent 负责 |
|---|---|---|---|---|
| 1. 需求启动 | 把一句需求变成正式开发任务 | 需求记录、分支、需求目录 | 明确业务目标和优先级 | 创建任务、建分支、保存原始需求 |
| 2. 需求澄清 | 消除模糊点 | 澄清问题清单、业务边界、待确认项 | 回答关键业务问题 | 追问遗漏、检索上下文、标记不确定信息 |
| 3. Spec 编写 | 把需求变成 AI 可执行契约 | `proposal.md` / `spec.md` | 审核需求边界和验收标准 | 生成结构化 Spec |
| 4. 技术方案与任务拆解 | 明确怎么做 | `design.md`、`tasks.md` | 审方案、控范围 | 生成方案、拆原子任务 |
| 5. AI 实现 | 按任务施工 | 代码、测试、任务进度 | 在关键点介入 | 编码、更新任务状态、修编译问题 |
| 6. 自检与验证 | 先于人工 Review 消灭明显问题 | 测试结果、代码自审报告 | 判断高风险逻辑 | 跑测试、做代码自审、修复问题 |
| 7. MR / PR 创建 | 形成可审查变更 | MR 标题、描述、关联需求 | 确认提交内容 | 汇总 diff、生成 MR 描述 |
| 8. Review 与修复 | 完成人工和 AI 交叉审查 | Review 评论、修复提交 | 决定采纳哪些意见 | 辅助审查、定位评论、批量修复 |
| 9. 归档与知识沉淀 | 让经验进入下一次需求 | 更新后的 specs、context、notes | 审核沉淀内容 | 归档 Spec、提取经验、更新知识库 |

## 最小可执行版本

第一版不要追求复杂 Agent 网络，建议只保留 5 个核心动作：

1. 新建需求：创建需求目录、开发分支、原始需求文档。
2. 生成 Spec：输出需求背景、功能范围、非目标、验收标准、边界条件。
3. 生成 Plan：输出技术方案、文件影响、任务拆解、测试计划。
4. 执行与验证：AI 按任务实现，每个任务必须带编译、测试或可观察证据。
5. 归档知识：合并后把本次 Spec、踩坑、约束、可复用模板沉淀到项目知识库。

## Harness Engineering 机制

在新需求开发场景中，Harness Engineering 应该表现为 6 个机制。

| 机制 | 作用 |
|---|---|
| 上下文机制 | 让 AI 在正确阶段拿到正确的信息，例如 `AGENTS.md`、`context/`、Spec、历史需求、工程规范 |
| 流程机制 | 把需求开发拆成标准阶段：需求澄清、Spec、Plan、实现、验证、Review、归档 |
| 门禁机制 | 规定哪些阶段必须停下来确认，例如 No Spec No Code、Plan Review、测试通过、人工 Review |
| 工具机制 | 用 Command、Skill、MCP、代码索引、CI/CD，把重复流程自动化 |
| 反馈机制 | AI 犯错后，不只是修代码，还要修规则、模板、测试或知识库，避免同类错误复发 |
| 知识复利机制 | 每个需求结束后，把可复用经验沉淀到团队知识资产里，让下一次需求更快、更准 |

## 第一版强制门禁

| 门禁                | 规则                                |
| ----------------- | --------------------------------- |
| No Spec, No Code  | 没有经过确认的 Spec，不允许进入编码              |
| Plan Review       | `tasks.md` 必须经过人工确认，建议单次不超过 15 项  |
| Evidence Required | 每个任务完成后必须给出验证证据                   |
| AI Self Review    | 提 MR / PR 前必须先跑一次 AI 自审           |
| Human Review      | AI Review 只能辅助，最终由人判断             |
| Archive Required  | MR / PR 合并后必须归档 Spec 和经验，否则知识不会复利 |

## 可借鉴点

- 用 `propose -> apply -> archive` 把一次需求变成可追溯变更。
- 用“需求创建 -> 澄清 -> 计划 -> 执行 -> Review -> MR -> 发布”覆盖端到端研发链路。
- 用需求生命周期、阶段门禁和 `context/` 知识库形成团队复利。
- 用 Command / Skill / Agent 分层：Command 做快捷入口，Skill 封装专业流程，Agent 承担独立上下文中的复杂任务。

## 不建议照搬点

- 不建议一开始就建设几十个 Agent、Skill 和命令。应先用最小流程跑通真实需求，再按高频痛点逐步工具化。
- 不建议把 Harness Engineering 设计成某个专职角色的职责。它应该是团队共同维护的工程体系。
- 不建议追求“0 人工 Coding”作为第一目标。更合理的第一目标是“需求、方案、验证和知识沉淀可控”。

## 下一步分析方向

第 2 组应继续分析 Spec / SDD 方法，重点确定：

- `spec.md` 应包含哪些字段。
- `design.md` 应如何表达技术方案和约束。
- `tasks.md` 如何拆到适合 AI 执行的粒度。
- 验收标准如何写成可测试、可审查、可追溯的形式。
