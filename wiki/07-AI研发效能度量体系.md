# 07-AI研发效能度量体系

## 1. 本文目标

本文面向已经开始引入 AI 研发流程的团队，回答三个问题：

- AI Coding 到底有没有真实价值？
- 如果效果不好，问题出在模型、Spec、知识库、样板间、Prompt，还是验证流程？
- 如何用数据驱动 Harness Engineering 体系持续改进？

本组案例主要来自：

- `拒绝“感觉有效”：用数据证明 AI Coding 的真实团队价值【天猫AI Coding实践系列】`
- `AI Coding思考：从工具提效到范式变革，我们还缺什么？`
- `认知重建之后，步入Agentic Engineering的工程革命`

本文强调：度量不是为了考核工程师，而是为了让团队知道工程体系哪里有效、哪里失效、下一步应该优化什么。

## 2. 核心原则

AI 研发效能不能只靠体感判断。

体感容易受到三类偏差影响：

- 幸存者偏差：成功案例被反复传播，失败尝试无人记录。
- 归因错误：需求交付变快，可能是需求本身简单，不一定是 AI 有效。
- 个体差异：少数高手提升明显，不代表团队整体提升。

所以度量体系必须同时回答三类问题：

| 问题 | 对应指标层 | 典型用途 |
| --- | --- | --- |
| AI 在哪些场景可靠？ | 质量指标 | 判断能力边界、模型选择、场景分流 |
| AI 出码链路哪里卡住？ | 链路指标 | 诊断 Spec、知识库、样板间、Skills 是否有效 |
| AI 对真实交付贡献多少？ | 结果指标 | 证明需求覆盖率、代码采纳率、Token 成本 |

三层指标必须相互校验。只看结果指标会导致盲调；只看离线评测会脱离生产；只看工具调用会把“用了”误判为“有用”。

## 3. 三层指标总览

```text
质量指标：离线评测
  目标：知道 AI 在什么场景能稳定完成，什么场景不能。
  产物：评测集、复杂度矩阵、结果分、行为分、能力热力图。

链路指标：在线过程诊断
  目标：知道上下文和工具有没有真正起作用。
  产物：调用率、命中率、关联采纳率、四象限分析、零结果查询。

结果指标：真实交付证明
  目标：知道 AI 参与了多少需求，贡献了多少最终上线代码，消耗多少成本。
  产物：需求覆盖率、代码采纳率、Token 成本、交付效率、质量滞后指标。
```

推荐工作流：

1. 用质量指标建立能力基线。
2. 用链路指标定位生产过程问题。
3. 用结果指标验证真实交付价值。
4. 根据数据更新 Spec、规则、知识库、样板间和验证门禁。

## 4. 质量指标：建立能力边界

质量指标是离线评测，用来判断 AI 在团队真实业务场景中的能力边界。

不要直接照搬通用 Benchmark。通用评测只能说明模型在公开问题上的能力，不能说明它在团队组件库、业务规则、代码规范和内部平台上的表现。

### 4.1 评测集来源

评测用例应来自真实历史需求。

每条用例至少包含：

```markdown
# eval-id

## 需求背景

## 输入材料

- PRD 或需求描述：
- 相关 Spec：
- 可用组件文档：
- 可用领域知识：
- 参考样板间：

## 期望产出

- 需要新增或修改的能力：
- 不允许修改的范围：
- 验收标准：

## 参考答案点 refAnswers

- 必须满足的业务点 1：
- 必须满足的业务点 2：
- 必须满足的异常处理：

## 客观测试 testCases

- 可运行测试：
- 页面检查：
- 接口校验：

## 过程要求

- 必须查阅的知识：
- 必须调用的工具：
- 必须遵守的规则：
```

第一版评测集不追求大，建议先准备 20 到 30 条高质量用例，覆盖团队最高频的新需求类型。

### 4.2 复杂度矩阵

复杂度矩阵用于判断哪些场景适合 AI 主导，哪些场景需要人机协作，哪些场景暂不适合。

以中后台新需求为例，可以使用“业务复杂度 × 物料成熟度”两维矩阵。

| 业务复杂度 | 说明 | 示例 |
| --- | --- | --- |
| L1 标准化 | 直接映射到标准组件和标准流程 | CRUD 列表、简单表单、详情页 |
| L2 有联动 | 存在状态依赖、字段联动、流程流转 | 表单联动、多级筛选、审批流 |
| L3 复杂交互 | 超出常规组件覆盖，需要架构设计 | 拖拽、画布、复杂编辑器、微前端集成 |

| 物料成熟度 | 说明 |
| --- | --- |
| C1 完善 | 有组件、文档、示例、样板间 |
| C2 部分完善 | 有组件或代码，但文档和示例不足 |
| C3 缺失 | 需要新建组件、探索方案或补齐知识 |

九象限分流建议：

| 区域 | 象限 | 建议 |
| --- | --- | --- |
| 推荐区 | L1-C1、L1-C2、L2-C1 | 可让 AI 主导，人工验收 |
| 调试区 | L1-C3、L2-C2、L3-C1 | 人机协作，多轮验证 |
| 挑战区 | L2-C3、L3-C2、L3-C3 | 先补物料或由人主导方案 |

这个矩阵的价值不是贴标签，而是指导行动：

- 需求分流：新需求进入前先判断适配方式。
- 能力提升：通过补组件文档、样板间和知识，把 C2/C3 推向 C1。
- 预期管理：让业务方知道哪些需求 AI 可独立完成，哪些需要人主导。

### 4.3 双评分模型

企业场景不能只看最终代码是否跑通，还要看 AI 是否按正确流程工作。

建议采用“结果分 + 行为分”：

| 分数 | 评判内容 | 第一版建议权重 |
| --- | --- | --- |
| 结果分 | 代码是否满足业务需求、测试是否通过 | 70% 到 80% |
| 行为分 | 是否查阅知识、调用工具、遵守流程 | 20% 到 30% |

公式示例：

```text
综合得分 = 结果分 * 0.75 + 行为分 * 0.25
```

结果分可以由三部分组成：

- LLM as Judge：评估 refAnswers 是否满足。
- 自动化测试：评估客观可测的逻辑。
- 人工抽检：校准 LLM 评分是否可靠。

行为分可以检查：

- 是否阅读当前需求 Spec。
- 是否使用正确样板间。
- 是否检索领域知识。
- 是否调用组件文档工具。
- 是否先 Plan 后编码。
- 是否执行验证命令。

行为分不是为了惩罚 AI，而是为了识别“碰巧正确”。一个没查文档却写对的 Agent，在简单场景可能可用，但在复杂场景风险更高。

### 4.4 能力热力图

每轮离线评测后，把得分聚合到复杂度矩阵中，形成能力热力图。

建议看四类信息：

- 哪些象限得分高，可以放入 AI 主导场景。
- 哪些象限得分低，需要补物料或改流程。
- 哪些模型在同一象限差异明显。
- 哪些调优动作带来得分提升。

典型闭环：

```text
热力图发现 L2-C2 得分低
→ 下钻失败用例
→ 发现表单联动规则描述不足
→ 更新 SPEC 模板，补联动规则表和流程图
→ 补组件文档或样板间
→ 重新评测
→ 验证 L2-C2 得分是否提升
```

## 5. 链路指标：诊断过程瓶颈

链路指标用于判断团队准备的上下文、知识库、组件文档、Spec 和 Skills 是否真正发挥作用。

核心问题：

> AI 生成代码时，是否查到了该查的资料？查到后是否真的改善了最终代码？

### 5.1 上下文漏斗

上下文能力建议统一使用三级漏斗：

```text
调用率 → 命中率 → 关联采纳率
```

定义：

| 指标 | 公式 | 说明 |
| --- | --- | --- |
| 调用率 | 调用某能力的会话数 / 应调用会话数 | AI 是否知道要用这个能力 |
| 命中率 | 返回有效结果的调用数 / 总调用数 | 知识或组件是否覆盖需求 |
| 关联采纳率 | 使用某能力的会话最终代码采纳率 | 查到的内容是否真的有用 |

异常解释：

| 异常 | 可能原因 | 优化动作 |
| --- | --- | --- |
| 调用率低 | Prompt 没引导、Skill 未触发、流程缺门禁 | 更新规则、增加触发条件、在 Plan 阶段强制列出检索项 |
| 命中率低 | 知识缺失、索引差、命名不一致 | 补知识、改索引、增加同义词 |
| 命中率高但采纳率低 | 内容不可操作、示例不足、召回不精准 | 重写知识、补示例、拆分条目 |

### 5.2 四象限分析

对每条知识、组件文档、Spec 模板或 Skill，按“使用频率 × 关联采纳率”分布到四象限。

| 象限 | 含义 | 动作 |
| --- | --- | --- |
| 高频高效 | 经常被用且效果好 | 标杆保留，推广到模板 |
| 高频低效 | 经常被用但效果差 | 优先修复 |
| 低频高效 | 偶尔被用但效果好 | 改触发条件，提高可发现性 |
| 低频低效 | 很少被用且效果差 | 归档、合并或删除 |

高频低效是最优先处理的区域。因为它被频繁召回，影响面最大。

### 5.3 需要追踪的上下文资产

建议至少追踪四类资产。

| 资产 | 追踪指标 | 诊断问题 |
| --- | --- | --- |
| SPEC 模板 | 使用次数、关联采纳率、返工轮次 | 模板结构是否足够清晰 |
| 领域知识 | 调用率、命中率、关联采纳率、零结果查询 | 知识是否覆盖真实问题 |
| 组件/平台文档 | 查询次数、命中率、示例命中率 | AI 是否能正确使用内部组件 |
| Skills/工作流 | 触发率、完成率、关联采纳率 | 标准流程是否被正确触发和完成 |

### 5.4 零结果查询

零结果查询是知识库缺口的直接信号。

每周输出 Top 20 零结果查询，并按两个维度排序：

```text
优先级 = 出现频次 × 业务影响
```

处理方式：

- 高频且重要：立即补知识或组件文档。
- 高频但不重要：增加澄清或重定向。
- 低频但重要：进入领域负责人待办。
- 低频且不重要：暂不处理。

## 6. 结果指标：证明真实交付价值

结果指标必须从 IDE 内接受补全，延伸到代码合并和需求上线。

核心口径：

> 最终上线代码中，有多少来自 AI？AI 参与了多少真实需求？为这些需求消耗了多少成本？

### 6.1 数据关联键

结果指标依赖跨系统关联。

第一版建议用以下关联键：

```text
(repo_project, branch)
```

数据来源：

| 数据 | 来源 | 用途 |
| --- | --- | --- |
| AI 任务记录 | AI 编码平台或 IDE 插件 | 识别会话、模型、Token、生成 Diff |
| 需求记录 | 需求/迭代系统 | 识别业务需求、负责人、状态 |
| 代码记录 | Git 平台 | 识别最终合并 Diff |
| 发布记录 | 发布系统 | 判断代码是否上线 |
| 缺陷记录 | 缺陷系统 | 观察质量滞后指标 |

基础数据流：

```text
AI 出码后上报 Diff
→ 需求系统记录 repo_project 和 branch
→ 发布或合并后同步 Merge Commit
→ 定时任务计算 AI Diff 与最终 Diff 的采纳关系
→ 生成需求级、迭代级、团队级指标
```

### 6.2 需求覆盖率

定义：

```text
需求覆盖率 = 关联 AI 任务的需求数 / 总需求数
```

用途：

- 看 AI 在团队真实需求中的渗透程度。
- 判断哪些业务域还没有被覆盖。
- 识别工具不好用、场景不适配或流程未推广的问题。

注意：

- 覆盖率高不等于效果好。
- 覆盖率需要和采纳率、返工轮次、质量指标一起看。

### 6.3 代码采纳率

定义：

```text
代码采纳率 = AI 生成代码被最终合并或上线的行数 / AI 生成代码总行数
```

建议口径：

- 以 Diff 行为单位计算。
- 同一分支多次 AI 出码需要合并后再计算。
- 与 Merge Commit 或最终上线 Diff 比对。
- 对代码做规范化处理，降低空格、注释、格式化差异造成的误判。

规范化处理可以包括：

- 去除纯注释行。
- 合并连续空白。
- 统一引号和分号风格。
- 排除格式化工具造成的大面积无语义变更。

采纳率解释：

| 情况 | 可能含义 |
| --- | --- |
| 高采纳 + 低返工 | 出码稳定，物料有效 |
| 高采纳 + 高缺陷 | AI 代码被合入但质量门禁不足 |
| 低采纳 + 高 Token | 高成本低收益，需要重点诊断 |
| 低采纳 + 高覆盖 | 团队大量尝试但流程或物料不成熟 |

### 6.4 Token 成本

定义：

```text
需求 Token 成本 = 关联到该需求的所有 AI Task Token 总量
```

可按以下维度聚合：

| 维度 | 用途 |
| --- | --- |
| Task | 分析单次会话是否低效 |
| 需求 | 评估单个需求投入产出 |
| 迭代 | 观察一个周期内的 AI 使用成本 |
| 团队 | 看整体趋势和预算 |
| 模型 | 比较不同模型的成本收益 |

Token 成本应和采纳率一起看：

- 高 Token、高采纳：可能是复杂需求，投入合理。
- 高 Token、低采纳：优先复盘 Prompt、Spec、上下文和任务拆分。
- 低 Token、高采纳：可沉淀为高效样板流程。

### 6.5 辅助结果指标

辅助指标不建议第一天就作为核心目标，但应逐步补齐。

| 指标 | 用途 | 注意事项 |
| --- | --- | --- |
| 单需求交付周期 | 观察交付效率 | 受需求复杂度影响大，需要分层对比 |
| 返工轮次 | 观察首版质量 | 需要定义什么算一轮返工 |
| 缺陷率 | 观察上线质量 | 滞后指标，需要积累周期 |
| Review 问题数 | 观察代码质量 | 要区分风格问题和语义问题 |
| 验证通过率 | 观察门禁有效性 | 如果永远通过，可能门禁太弱 |

## 7. 看板设计

第一版看板不需要复杂，但必须能支持下钻。

### 7.1 团队总览看板

展示：

- 总需求数。
- AI 参与需求数。
- 需求覆盖率。
- 代码采纳率。
- Token 总成本。
- 平均单需求 Token。
- 平均返工轮次。
- 质量热力图摘要。

### 7.2 能力边界看板

展示：

- 复杂度矩阵热力图。
- 各象限得分。
- 各模型得分对比。
- 失败用例列表。
- 最近一次调优前后对比。

用途：

- 决定哪些需求可以 AI 主导。
- 决定优先补哪些物料。
- 决定是否切换模型或调整 Prompt。

### 7.3 链路诊断看板

展示：

- SPEC 模板使用频率和关联采纳率。
- 知识库调用率、命中率、关联采纳率。
- 组件文档零结果查询 Top 20。
- Skill 触发率、完成率、关联采纳率。
- 高频低效资产列表。

用途：

- 每周运营知识库和样板间。
- 识别无效或误导性知识。
- 判断工作流是否被触发。

### 7.4 需求下钻看板

每个需求应能看到：

- 需求名称和状态。
- 关联仓库和分支。
- 关联 AI 任务。
- 使用模型。
- Token 成本。
- AI 生成 Diff。
- 最终合并 Diff。
- 代码采纳率。
- 关联 Spec 模板。
- 命中的知识和样板间。
- 验证结果和缺陷记录。

需求下钻看板用于复盘，不用于排名个人。

## 8. 每周运营机制

度量必须进入固定节奏，否则会变成一次性报表。

建议每周 30 到 60 分钟做一次 AI 研发效能运营会。

### 8.1 固定议程

1. 看结果指标：覆盖率、采纳率、Token 成本是否异常。
2. 看链路指标：调用率、命中率、采纳率是否有断点。
3. 看高频低效资产：本周修哪 3 条知识或样板间。
4. 看零结果查询：本周补哪 5 条知识。
5. 看失败需求：是否需要更新 Spec、规则、样板间或验证门禁。
6. 看离线评测：是否需要重新跑基线。

### 8.2 调优动作分类

| 数据现象 | 优先动作 |
| --- | --- |
| 某类需求采纳率低 | 优先检查 Spec 模板和样板间 |
| 知识调用率低 | 检查 Prompt、AGENTS、Skill 触发条件 |
| 知识命中率低 | 补知识、改索引、补同义词 |
| 命中率高但采纳率低 | 重写知识，增加可执行示例 |
| Token 高但采纳低 | 拆任务，减少无效上下文，要求先 Plan |
| 验证总是通过但缺陷多 | 增强测试和门禁 |
| 离线高分但线上低采纳 | 检查评测集是否脱离真实生产 |

### 8.3 数据到资产的闭环

每次运营会必须产出资产改进项，而不是只汇报数字。

资产改进项包括：

- 更新 SPEC 模板。
- 更新 `AGENTS.md`。
- 新增或修订样板间。
- 新增或修订领域知识。
- 增加验证脚本。
- 调整 Skill 触发条件。
- 更新离线评测用例。

## 9. 数据采集最小方案

如果团队没有完整平台，第一版可以用轻量方案先跑起来。

### 9.1 必采字段

AI Task：

## 10. 指标使用红线

AI 研发效能指标很容易被误用，必须提前设红线。

### 10.1 不用于个人排名

不要用 AI 采纳率排名工程师。

原因：

- 不同人负责的需求复杂度不同。
- 不同模块物料成熟度不同。
- 高风险需求本来就需要更低的 AI 自由度。

正确用法是按场景、团队、模板、知识、模型和流程看趋势。

### 10.2 不追求单一指标最大化

错误目标：

- 只追求覆盖率，导致不适合 AI 的需求也强行使用。
- 只追求采纳率，导致团队不愿让 AI 尝试复杂任务。
- 只追求低 Token，导致上下文不足、质量下降。

正确目标：

- 在适合的场景提高覆盖率。
- 在标准化场景提高采纳率。
- 在质量稳定前提下降低 Token 成本。
- 在复杂场景通过物料建设扩大 AI 可用边界。

### 10.3 不把接受补全等同于业务价值

IDE 内接受补全只是中间行为，不代表最终有用。

真实价值必须看：

- 是否进入最终合并代码。
- 是否随需求上线。
- 是否减少返工。
- 是否没有引入额外缺陷。
- 是否沉淀为可复用资产。

## 11. 第一版落地清单

### 11.1 第 1 周：定义口径

- 明确需求覆盖率、代码采纳率、Token 成本口径。
- 确定关联键：优先使用 `(repo_project, branch)`。
- 确定需求复杂度和物料成熟度分级。
- 选定 2 到 3 个试点需求类型。

### 11.2 第 2 周：采集数据

- 记录 AI Task 元数据。
- 保存 AI 生成 Diff。
- 关联需求、仓库、分支。
- 记录 Spec 模板、样板间、知识命中。
- 记录 Token 消耗。

### 11.3 第 3 周：建立看板

- 做团队总览。
- 做需求下钻。
- 做知识调用漏斗。
- 做样板间和 Spec 模板采纳率统计。

### 11.4 第 4 周：形成运营闭环

- 每周输出一次效能报告。
- 每周修复一批高频低效知识。
- 每周补充零结果查询 Top 项。
- 每两周更新一次离线评测集。
- 每月复盘 AI 可主导场景是否扩大。

## 12. 交付标准

一套 AI 研发效能度量体系算合格，需要满足：

- 能区分不同需求复杂度和物料成熟度。
- 有离线评测集和能力热力图。
- 有结果分和行为分。
- 能追踪 Spec、知识库、样板间、Skills 的调用和关联采纳。
- 能以需求为单位计算 AI 参与覆盖率。
- 能以 Diff 为单位计算代码采纳率。
- 能追踪需求级 Token 成本。
- 能下钻到失败需求和低效资产。
- 每周能产出明确的资产改进动作。
- 指标用于改进系统，不用于个人排名。

最终目标不是证明“AI 很厉害”，而是让团队知道：哪些场景可以放心交给 AI，哪些场景要补物料，哪些流程需要门禁，哪些知识正在产生复利。
