# 知识沉淀与复利机制

## 适用范围

本文基于 `raw/` 中第 5 组“知识沉淀”材料整理，面向新需求开发场景。目标是定义团队如何把每次需求中的经验、决策、规则、坑点和业务理解沉淀成 AI 可消费、团队可共享、长期可演进的知识资产。

参考材料：

- `Harness不是目的，知识才是护城河 —— 一个AI工程交付团队的知识沉淀实践.md`
- `AI Coding思考：从工具提效到范式变革，我们还缺什么？.md`
- `认知重建之后，步入Agentic Engineering的工程革命.md`

## 核心结论

工作流只是管道，知识才是流过管道的活水。Harness Engineering 的长期价值不在于某次流程自动化，而在于每次需求都让团队知识变厚，让下一次 AI 执行更准、更快、更少返工。

企业级 AI Coding 的主要瓶颈不是“AI 能不能执行任务”，而是“人类如何准确、高效、规模化地把复杂目标传达给 AI”。专家知识越体系化，目标传达的信息熵越低，AI 成功率越高。

一句话原则：

> 工具会换，模型会变，工作流会重构；但团队沉淀的领域模型、架构决策、业务规则、最佳实践和已知坑点，会持续成为 AI 研发效率的护城河。

## 知识沉淀的目标

知识沉淀不是为了写文档，而是为了让后续需求自动受益。

| 目标 | 说明 |
|---|---|
| 降低目标传达成本 | 不再每次靠人把背景重新讲一遍 |
| 降低 AI 猜测空间 | 让 AI 基于团队事实工作 |
| 降低重复踩坑 | 让错误变成规则、清单或知识 |
| 提升团队一致性 | 所有人和所有 Agent 使用同一套上下文 |
| 加速新人上手 | 新成员 clone 仓库即可获得团队公共记忆 |
| 形成复利 | 每个需求都让下一次需求启动成本更低 |

## 五层知识存储

建议按共享边界和生命周期分层：

| 层级 | 名称 | 存放位置 | 说明 |
|---|---|---|---|
| Layer 0-P | 个人偏好 | `~/.ai/` 或个人配置 | 个人习惯，不强加给团队 |
| Layer 0-T | 团队约定 | `context/team/` | 团队通用规范、Review 标准、Git 规范 |
| Layer 1 | 技术知识 | `context/tech/` | 跨项目通用技术模式、反模式、组件经验 |
| Layer 2 | 业务知识 | `context/biz/{domain}/` | 领域模型、业务流程、业务规则 |
| Layer 3 | 项目知识 | `context/project/` | 当前项目架构、接口、部署、模块知识 |

新需求中产生的知识默认先进入 Layer 3。归档时判断是否可提升：

```text
项目内知识
  ├── 仅当前项目有效 -> 留在 Layer 3
  ├── 通用技术经验 -> 提升到 Layer 1
  └── 通用业务规则 -> 提升到 Layer 2
```

## 五种知识类型

每条知识只归入一种主类型，避免混乱。

| 类型 | 定义 | 示例 |
|---|---|---|
| `model` | 实体、数据结构、关系 | 订单包含支付单、履约单、售后单 |
| `decision` | 技术或架构决策及原因 | 选择事件驱动而不是同步 RPC，因为需要解耦状态变更 |
| `guideline` | 推荐做法或禁止做法 | recommend: 公共模块变更后必须跑兼容性检查 |
| `pitfall` | 已知风险、故障模式、排查步骤 | 某缓存 key 未带租户 ID 会导致串数据 |
| `process` | 业务流程、状态机、操作步骤 | 提交 -> 审核 -> 发布 -> 回滚 |

## 三级成熟度

知识不是写完就可信。建议引入成熟度：

| 成熟度 | 含义 | 进入条件 |
|---|---|---|
| `draft` | 新提取、单一来源 | 从一次需求、一次 Review、一次故障中提取 |
| `verified` | 单项目验证 | 至少在一个工作流或项目中被成功引用 |
| `proven` | 多项目验证 | 至少两个不同项目或多名成员验证有效 |

成熟度升级规则：

```text
draft
  -> 被一次需求成功引用
  -> verified
  -> 被两个以上项目或成员验证
  -> proven
```

成熟度也要能下降：

| 情况 | 处理 |
|---|---|
| 长期未引用 | 降低成熟度或移出活跃索引 |
| 被标记过时 | 标记 deprecated，等待确认 |
| 被反例推翻 | 标记 contradiction，进入人工审核 |
| draft 长期无人使用 | 归档 |

## 三级渐进式索引

知识消费要按需，不要一次性推送。建议采用三级索引：

| 索引层 | 文件 | 内容 | 目标 |
|---|---|---|---|
| Layer A | `knowledge-catalog.md` | 全景目录，约 50 行 | 知道知识库有什么 |
| Layer B | 各目录 `catalog.md` | 分类清单，约 100-300 行 | 找到相关条目 |
| Layer C | 具体知识条目 | 完整内容，约 50-200 行 | 读取可执行知识 |

查询路径：

```text
读 knowledge-catalog.md
  -> 选择分类 catalog.md
  -> 根据 tags / phase / maturity 筛选条目
  -> 读取具体知识条目
  -> 必要时追溯原始需求或 PR
```

好处：

- Agent 用很少上下文了解知识库全貌。
- 只在真正需要时读取完整内容。
- 避免把 50 条完整知识一次性塞进上下文。

## 查询预算

每个阶段应限制知识查询范围，避免上下文膨胀。

| 阶段 | 查询焦点 | 重点知识类型 |
|---|---|---|
| 需求澄清 | 业务知识、历史需求 | `model`、`process`、`pitfall` |
| 技术方案 | 技术知识、历史决策 | `decision`、`guideline`、`pitfall` |
| 架构设计 | 架构模式、实体关系 | `decision`、`model` |
| 编码实现 | 编码实践、团队约定 | `guideline`、`pitfall` |
| 测试验证 | 反模式、故障案例 | `pitfall`、`guideline` |
| 归档 | 全流程产物 | 所有类型 |

原则：知识消费要精准，不要贪婪。

## 工作流中的知识闭环

每个需求都应该经过三段知识流：

```text
INIT: 知识注入
  -> 读取知识索引和当前项目上下文

RUN: 知识消费
  -> 各阶段按需查询知识
  -> 在产物中记录 knowledgeReferences

ARCHIVE: 知识提取
  -> 从 spec/design/tasks/review/notes/log 中提取新知识
  -> 判断层级、类型、成熟度
  -> 更新索引
```

产物中建议记录引用：

```json
{
  "knowledgeReferences": [
    {
      "id": "TK-001",
      "title": "分页查询延迟关联优化",
      "usedIn": "Design: 查询性能方案"
    }
  ]
}
```

归档阶段读取这些引用，更新 `last_referenced` 和成熟度。

## 什么值得沉淀

值得沉淀：

| 类型 | 判断标准 |
|---|---|
| 重复出现的问题 | AI 或人已经踩过，未来大概率还会遇到 |
| 业务领域规则 | 模型无法从公开知识中获得 |
| 架构决策原因 | 只知道“怎么做”不够，还需要知道“为什么” |
| 高风险坑点 | 一旦犯错会导致线上问题、数据问题、安全问题 |
| 代码定位知识 | 业务术语和代码入口之间的映射 |
| 标准流程 | 新人或 AI 需要反复执行 |
| 反例 | 告诉 AI 什么不能做，比只写正例更有效 |

不值得沉淀：

| 类型 | 原因 |
|---|---|
| 一次性问题 | 未来复用概率低 |
| 公开通用知识 | 模型本身已掌握，或官方文档容易获得 |
| 过细实现细节 | 容易过期，且占用上下文 |
| 简单自然对话能解决的问题 | 没必要永久化 |
| 未经验证的猜测 | 只能作为 draft，不能进入高优先级索引 |

## notes.md 的作用

`notes.md` 是需求执行过程中的“知识暂存区”。不要要求一开始就写成完美知识条目。

建议格式：

```markdown
# Notes

## 发现
- 

## AI 犯错记录
- 错误：
- 原因：
- 修复：
- 是否值得沉淀：

## 待沉淀知识
- [ ] 类型：
  - 内容：
  - 建议层级：
  - 证据：
```

原则：先记下来，再归档整理。不要因为格式不完美而丢失知识原料。

## 知识审核机制

知识库会影响所有后续 AI 行为，必须有轻量审核。

| 操作 | 审核方式 |
|---|---|
| 新增 draft | 可自动进入暂存区 |
| draft -> verified | 至少一次成功引用或人工确认 |
| verified -> proven | 多项目 / 多人验证，maintainer 审核 |
| 删除或废弃知识 | 需要说明原因 |
| 标记 contradiction | 必须人工裁决 |
| 修改核心业务规则 | 必须 Review |

推荐角色：

| 角色 | 权限 |
|---|---|
| maintainer | 裁决冲突、审批 proven、维护索引 |
| contributor | 贡献、验证、标记问题 |
| reader | 消费知识，不直接修改 |

## 知识冲突处理

| 冲突类型 | 处理 |
|---|---|
| 纯新增 | 自动合并 |
| 证据追加 | 自动合并 evidence |
| 成熟度提升 | 自动合并或轻审核 |
| 内容重复 | 合并为一条，保留别名 |
| 内容矛盾 | 标记 contradiction，人工裁决 |
| 成熟度冲突 | 保留较低成熟度，等待验证 |

## 知识 Lint

知识库不能只进不出。建议定期执行知识 Lint。

检查项：

| 检查 | 处理 |
|---|---|
| 索引不一致 | 自动修复 |
| 孤儿条目 | 降级或归档 |
| 长期未引用 draft | 移出活跃索引 |
| 过时技术栈 | 标记 deprecated |
| 重复条目 | 合并 |
| 无证据 proven | 降级 |
| 无失效条件的规则 | 要求补充 |

触发方式：

- 每完成 10 个需求自动触发。
- 每月固定触发。
- 手动执行 `/knowledge lint`。
- 知识库连续 30 天未清理时提醒。

## 文档即记忆

优先使用 Markdown + Git 管理知识，而不是一开始就建设复杂知识平台。

原因：

| 优点 | 说明 |
|---|---|
| 人和 AI 读同一份文件 | 避免“人用文档”和“AI 用知识库”版本漂移 |
| Git 天然版本化 | 可以 Review、diff、回滚、追责 |
| 可迁移 | 不绑定某个 Agent 工具或平台 |
| 高频使用对抗腐化 | 文档被 AI 每天消费，过时会更快暴露 |
| clone 即共享 | 新成员获得完整团队记忆 |

向量检索、RAG、MCP 可以作为消费方式，但不应替代结构化源文件。

## 第一版落地建议

第一阶段不需要完整知识中台，先做最小闭环：

1. 建立 `context/team/` 和 `context/project/`。
2. 为每个目录建立 `INDEX.md` 或 `catalog.md`。
3. 每个需求有 `notes.md`。
4. 归档阶段从 `notes.md`、Review、测试结果中提取知识。
5. 所有新知识先以 `draft` 进入。
6. 每次 AI 犯错至少判断一次：是否值得沉淀。
7. 每月做一次知识 Lint。

建议目录：

```text
context/
  knowledge-catalog.md
  team/
    catalog.md
    coding-standards.md
    review-guidelines.md
  tech/
    catalog.md
    patterns/
    pitfalls/
  biz/
    order/
      catalog.md
      models/
      processes/
      pitfalls/
  project/
    catalog.md
    architecture.md
    api-map.md
    deployment.md
    pitfalls/
```
