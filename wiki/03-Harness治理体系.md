# Harness 治理体系

## 适用范围

本文基于 `raw/` 中第 3 组“Harness 治理”材料整理，面向新需求开发场景。目标是定义 Harness Engineering 的工程控制系统：上下文、约束、流程、门禁、Agent 分工、反馈闭环和持续演进机制。

参考材料：

- `Harness Engineering：AI 能在真正"出事会炸"的后端系统里写代码吗？.md`
- `Harness Engineering：耗时一周，我是如何将应用的AI Coding率提升至90%的.md`
- `告别“氛围编程”：基于 Harness 治理和 SDD 的团队级 AI 研发范式演进与实践.md`

## 核心结论

Harness Engineering 不是岗位，也不是某个工具，而是一套围绕 AI Agent 构建的工程治理体系。

它解决的问题是：模型已经能写代码，但“能写”到“写了敢用”之间缺少系统性保障。Harness 的目标不是让 Agent 更聪明，而是让 Agent 的错误变得可控、可发现、可阻断、可修复，并把每次错误沉淀成下一次不会再犯的规则、测试、知识或工具。

一句话定义：

> Harness Engineering 是围绕 AI Agent 设计上下文架构、结构化约束、工作流控制、质量门禁、反馈回路和持续改进机制的系统工程实践。

## 为什么需要 Harness

裸用 AI Agent 常见失败模式：

| 失败模式 | 表现 | Harness 对策 |
|---|---|---|
| 一步到位 | 复杂需求塞进单次对话，后半程开始幻觉或遗漏 | 拆阶段、拆任务、限制上下文 |
| 过早宣布完成 | Agent 说完成了，但代码未编译、功能未实现 | 强制验证证据 |
| 过早标记功能完成 | 实现了局部逻辑，没有端到端验证 | 测试、日志、页面或接口验证 |
| 冷启动 | 每次会话重新理解项目，浪费上下文 | 持久化记忆、进度文件、索引 |
| 自我评价不可靠 | Agent 难以准确判断自己产物质量 | 执行 Agent 与评审 Agent 分离 |
| 规则漂移 | 语言化建议被忽略 | 机械化约束和质量门禁 |
| 熵累积 | AI 模仿次优模式，代码库逐渐腐化 | Golden Rules、自动扫描、定期治理 |

## Harness 四根支柱

| 支柱 | 说明 | 关键实践 |
|---|---|---|
| 上下文架构 | Agent 恰好获得当前任务需要的信息 | `AGENTS.md` 做索引，深层文档按需加载 |
| Agent 专业化 | 不同 Agent 承担规划、实现、验证、审查 | Planner / Generator / Evaluator 分离 |
| 持久化记忆 | 进度和决策保存在文件系统，而不是聊天上下文 | `summary.md`、`progress.md`、`notes.md` |
| 结构化执行 | 未经计划和门禁，不允许直接写代码 | 理解 -> 规划 -> 执行 -> 验证 |

## 推荐 Harness 架构

建议新项目采用 5 层 Harness 架构：

| 层级 | 目标 | 典型资产 |
|---|---|---|
| L1 项目宪法层 | 定义不可违背的原则 | `AGENTS.md`、`constitution.md` |
| L2 上下文层 | 让 Agent 知道项目是什么 | `context/`、知识库索引、架构文档、领域术语 |
| L3 约束层 | 让 Agent 不敢越界 | Rules、Lint、测试、权限、安全边界 |
| L4 执行层 | 让 Agent 按流程推进 | Command、Skill、任务清单、MCP 工具 |
| L5 反馈层 | 让错误变成规则和知识 | Review 报告、测试结果、踩坑记录、知识沉淀 |

对应目录可以这样设计：

```text
project/
  AGENTS.md
  constitution.md
  context/
    team/
    project/
    knowledge/
  harness/
    rules/
    skills/
    agents/
    checks/
    templates/
  requirements/
    REQ-001/
      summary.md
      proposal.md
      spec.md
      design.md
      tasks.md
      review/
      logs/
```

## 上下文治理

上下文治理的目标是“刚好够用”，不是越多越好。

| 层级       | 加载时机            | 内容                               | 原则            |
| -------- | --------------- | -------------------------------- | ------------- |
| L1 常驻上下文 | 每次会话默认加载        | `AGENTS.md`、核心规则、项目索引            | 短小，像地图，不像百科全书 |
| L2 阶段上下文 | 进入某阶段时加载        | 需求分析 Skill、编码 Skill、Review Skill | 当前阶段需要什么才加载什么 |
| L3 按需上下文 | Agent 遇到具体问题时检索 | 业务文档、历史需求、接口说明、踩坑记录              | 通过索引定位，避免盲目塞入 |

`AGENTS.md` 建议只做 5 件事：

1. 说明项目身份和技术栈。
2. 给出目录地图。
3. 指向规则、知识库、模板和工具。
4. 定义必须遵守的工作流。
5. 声明禁止事项和人工确认点。

不要把 `AGENTS.md` 写成大而全的知识库。所有内容都重要，等于没有内容重要。

## 约束治理

约束要尽量从“语言化期望”升级为“结构化约束”。

| 弱约束     | 强约束                             |
| ------- | ------------------------------- |
| 写高质量代码  | 必须通过 lint、test、review gate      |
| 记得写测试   | 测试任务阻塞代码审查任务                    |
| 注意安全    | 禁止明文日志、禁止拼接 SQL、CI 扫描失败不可合并     |
| 不要改无关文件 | 任务清单声明允许修改路径，超出路径必须确认           |
| 保持架构分层  | 通过 import rule、lint 或结构测试阻断跨层调用 |

约束分三类：

| 类型 | 例子 | 落地方式 |
|---|---|---|
| 权限约束 | 禁止生产写操作、禁止危险命令 | 沙箱、权限白名单、人工审批 |
| 架构约束 | 禁止跨层调用、禁止新增未批准依赖 | Lint、结构测试、Review checklist |
| 流程约束 | 未计划不得编码、测试未过不得 Review | 阶段门禁、任务依赖、状态机 |

关键原则：如果一条规则不能被机器检查，Agent 大概率会漂移。

## 工作流门禁

每个阶段都应有三件事：

- Entry Criteria：什么时候可以进入。
- Required Context：需要加载哪些规则、知识和 Skill。
- Quality Gate：产出满足什么条件才能离开。

建议第一版门禁：

| 阶段           | Entry Criteria | Quality Gate                                              | 失败回退         |
| ------------ | -------------- | --------------------------------------------------------- | ------------ |
| 需求澄清         | 有原始需求          | Blocking 疑问点已确认                                           | 回到需求补充       |
| Spec         | 需求边界明确         | 验收标准可测试，Non-Goals 明确                                      | 回到澄清         |
| Design       | Spec 已确认       | 每个设计点可追溯到 Spec                                            | 回到 Spec      |
| Tasks        | Design 已确认     | 任务原子化，每项有验证方法                                             | 回到 Design    |
| Implement    | Tasks 已确认      | 每项任务有验证证据                                                 | 回到对应 Task    |
| Self Review  | 代码完成           | AI 自审无 Critical / Major                                   | 回到 Implement |
| Test / CI    | 自审通过           | `status == success && total_tests > 0 && passed == total` | 回到测试或实现      |
| Human Review | 测试通过           | 人工确认可合并                                                   | 回到修复         |
| Archive      | 合并完成           | Spec、notes、知识库已同步                                         | 补齐归档         |

门禁要具体到可检查条件。不要只写“CI 通过”，要检查状态、测试数量和通过数量；不要只写“生成 Review 报告”，要检查文件存在、章节完整、问题分级清楚。

## Agent 分工

Harness 里最重要的分工是：做事的 Agent 和评判的 Agent 分离。

| Agent 类型 | 职责 | 工具权限 | 输出 |
|---|---|---|---|
| Planner | 理解需求、澄清问题、生成方案 | 读文档、读代码、检索知识 | `spec.md`、`design.md` |
| Generator | 按任务实现代码和测试 | 有限写权限、测试命令 | 代码、测试、任务状态 |
| Evaluator | 检查产物是否符合 Spec | 读代码、跑检查、生成报告 | Spec Compliance Report |
| Reviewer | 检查质量、安全、性能、可维护性 | 读 diff、读上下文 | Code Review Report |
| Maintainer | 归档、更新知识库、整理索引 | 文档写权限 | 更新后的 `context/`、`specs/` |

分工原则：

- Planner 不直接写生产代码。
- Generator 不评价自己是否合格。
- Evaluator 只看 Spec 与实现是否一致。
- Reviewer 关注质量问题，不代替人工最终判断。
- Maintainer 负责知识沉淀，但沉淀内容需要人审核。

## 反馈回路

Harness 的长期价值来自反馈闭环。

每次 AI 犯错后，不只修代码，还要判断应该修哪一层：

| 错误类型 | 应修复的 Harness 层 |
|---|---|
| 需求理解错 | Spec 模板、澄清问题、领域术语 |
| 找错代码位置 | 代码索引、业务术语到代码位置的映射 |
| 违反架构 | Rules、Lint、结构测试 |
| 忘记写测试 | Tasks 依赖、测试门禁 |
| Review 漏问题 | Review checklist、Reviewer Agent |
| CI 误判通过 | CI 结果解析规则 |
| 重复踩坑 | 知识库、反例、Skill |

建议采用“踩坑 -> 规则 -> 检查 -> 验证 -> 沉淀”的闭环：

```text
真实问题
  -> 归因
  -> 新规则 / 新测试 / 新模板 / 新知识
  -> A/B 或 Dry Run 验证
  -> 合入 Harness
  -> 后续需求自动受益
```

## Dry Run 机制

Harness 本身必须测试。不要拿真实需求直接验证第一版 Harness。

Dry Run 应覆盖：

| 检查点    | 要验证什么                        |
| ------ | ---------------------------- |
| 需求流程   | 是否能从原始需求生成 Spec、Design、Tasks |
| 门禁     | 未满足条件时是否真的阻断                 |
| 测试判断   | 是否识别 0 测试、失败测试、跳过测试          |
| Review | 是否生成报告，问题是否有分级和修复建议          |
| 回退     | CI 失败、需求不符时能否回到正确阶段          |
| 归档     | 是否同步 Spec、知识和变更记录            |

Dry Run 的目标不是证明 Harness 完美，而是低成本暴露流程缺陷。

## 人工确认点

Harness 不是全自动放权。人应该在高价值决策点介入。

建议保留这些人工确认点：

1. 需求边界确认。
2. Blocking 疑问点确认。
3. 技术方案确认。
4. 任务拆解确认。
5. 高风险代码 Review。
6. 部署或上线参数确认。
7. 最终合并和发布确认。
8. 知识沉淀内容确认。

人的职责不是逐行手写代码，而是定义边界、做取舍、验证结果、优化 Harness。

## 第一版落地建议

第一阶段不要追求“全自动”。建议优先建设 8 个最小资产：

| 资产 | 作用 |
|---|---|
| `AGENTS.md` | 项目入口索引和行为规则 |
| `constitution.md` | 项目不可违背原则 |
| `requirements/` | 需求全过程产物 |
| `context/project/` | 项目知识和领域规则 |
| `harness/rules/` | 机械化约束和检查规则 |
| `harness/skills/` | 需求、编码、测试、Review SOP |
| `harness/checks/` | 可执行门禁脚本或命令 |
| `summary.md` | 每个需求的阶段状态和追溯记录 |

第一版目标：

- 跑通 1 条真实小需求。
- 至少有 Spec、Design、Tasks、测试、自审、归档。
- 至少有 3 条机械化门禁。
- 至少把 1 个 AI 犯错案例沉淀为规则或模板。

## 不建议照搬点

- 不建议一开始建设庞大的多 Agent 网络。先用最小分工跑通流程。
- 不建议把所有知识塞进常驻上下文。应通过索引和按需加载治理。
- 不建议用 AI 自评替代外部验证。Agent 无法可靠评价自己的产物。
- 不建议把流程做成纯文档要求。关键规则必须能被机器检查或人工确认。
- 不建议追求高 AI 代码率本身。质量可控前提下的高 AI 代码率才有意义。

## 下一步分析方向

第 4 组应继续分析上下文与工程资产，重点确定：

- `AGENTS.md` 如何写成索引而不是百科全书。

- 新项目第一天应该准备哪些工程资产。
- 常驻上下文、阶段上下文、按需上下文如何组合。
