# Spec / SDD 方法与模板

## 适用范围

本文基于 `raw/` 中第 2 组“Spec / SDD 方法”材料整理，面向新需求开发场景。目标是定义团队可直接使用的 Spec-Driven Development 文件体系、字段模板、任务拆解规则和质量门禁。

参考材料：

- `2026 年 AI 编码的“渐进式 Spec”实战指南.md`
- `5 人 7 天干完 20 人数周的活：Spec-Driven Development 如何重新定义 AI 编程.md`
- `从 Vibe Coding 到范式编程：用 Spec 打造淘系交易的 AI 领域专家.md`

## 核心结论

Spec 不是更长的需求文档，而是人和 AI 之间的执行契约。它的价值不是让 AI 变聪明，而是减少 AI 的猜测空间，让 AI 在明确的边界、约束和验收标准内工作。

SDD 的核心原则：

1. No Spec, No Code：没有经过确认的 Spec，不进入编码。
2. Spec is Truth：文档和代码冲突时，优先修代码或同步修 Spec，不能让两者漂移。
3. WHAT / HOW 分离：Spec 描述做什么和为什么，Design 描述怎么做。
4. Acceptance Criteria 可测试：验收标准必须能被测试、Review 或人工验证。
5. Spec 是活文档：需求变化、实现偏差、Bug 修复都要同步更新 Spec。

## 文件体系

建议采用 5 类文件：

| 文件 | 定位 | 回答的问题 | 主要使用者 |
|---|---|---|---|
| `constitution.md` | 项目宪法 | 项目有哪些不可违背的原则和约束 | 所有需求、所有 Agent |
| `proposal.md` | 变更提案 | 为什么做、做什么、影响什么 | 人和 AI |
| `spec.md` | 需求规格 | 功能行为、边界、验收标准是什么 | 人和 AI |
| `design.md` | 技术方案 | 怎么实现、改哪些模块、关键决策是什么 | 人、AI、Reviewer |
| `tasks.md` | 执行清单 | AI 按什么顺序完成哪些原子任务 | AI、Reviewer |

如果团队想保持更轻量，可以合并为三文件：

| 文件 | 等价内容 |
|---|---|
| `spec.md` | `proposal.md` + 需求规格 |
| `design.md` | 技术方案 |
| `tasks.md` | 执行清单 |

## constitution.md 模板

`constitution.md` 是项目级约束，不随单个需求变化。它应短而硬，避免写成百科全书。

```markdown
# Project Constitution

## 架构原则
- 采用的架构分层：
- 禁止跨层调用：
- 模块边界：

## 技术约束
- 允许使用的框架 / 组件：
- 禁止引入的依赖：
- 数据库、缓存、消息、外部服务使用规范：

## 质量要求
- 必须包含的测试：
- 必须通过的检查：
- 性能、安全、稳定性底线：

## 代码规范
- 命名规范：
- 错误处理规范：
- 日志规范：

## AI 执行边界
- AI 可以自主修改的范围：
- 必须等待人工确认的场景：
- 禁止 AI 执行的操作：
```

## tasks.md 模板

`tasks.md` 是 AI 的施工清单。每个任务必须原子化、可验证、可回滚。

```markdown

## 执行原则
- 按顺序执行，未完成当前任务不得跳到后续任务。
- 每个任务完成后必须更新状态。
- 每个任务必须提供验证证据。

## 任务清单

### Task 1: 任务名称
- 目标：
- 依赖：
- 变更范围：
- 对应 Spec 条目：
- 验收标准：
- 验证命令 / 方法：
- 状态：Todo / Doing / Done

### Task 2: 任务名称
- 目标：
- 依赖：
- 变更范围：
- 对应 Spec 条目：

- 验证命令 / 方法：
- 状态：Todo / Doing / Done

## 变更摘要
> 全部完成后填写。

- 总文件数：
- 关键变更：
- 测试结果：
- Spec-Plan 偏差记录：
```

## 好 Spec 的判断标准

| 标准 | 说明 |
|---|---|
| 可测试 | 验收标准能通过测试、Review 或人工操作判断 |
| 有边界 | 明确 In Scope 和 Non-Goals |
| 少猜测 | 模糊点被列为待确认问题，不让 AI 自行脑补 |
| WHAT / HOW 分离 | Spec 不写具体实现细节，Design 再决定方案 |
| 可追溯 | 每个设计和任务能追溯到 Spec 条目 |
| 可迭代 | 需求变化时增量更新，而不是另起炉灶 |

一个简单检验方法：如果换一个技术栈实现，这份 Spec 仍然成立，说明粒度基本正确；如果 Spec 绑定了具体实现细节，通常是把 HOW 写进了 WHAT。

## 渐进式复杂度

不是所有需求都需要完整 SDD 流程。建议按复杂度分级：

| 需求类型 | 推荐流程 | 说明 |
|---|---|---|
| 微小变更 | 简短说明 + 直接修改 + 自检 | 文案、样式、小配置，不影响其他模块 |
| 小需求 | `spec.md` + `tasks.md` | 单模块、低风险、边界清晰 |
| 中等需求 | `proposal.md` + `spec.md` + `design.md` + `tasks.md` | 多模块、有接口或数据变更 |
| 大需求 | 多个 Spec 拆分 + 分阶段 Review + 多 Agent / 子任务 | 跨系统、高风险、强依赖知识库 |

原则：流程是可选增强，不是官僚化负担。越复杂、越高风险，越需要完整 Spec；越局部、越低风险，越应该轻量。

## 疑问点机制

AI 生成方案前必须主动暴露不确定因素，避免“生成后返工”。

疑问点格式：

```markdown
## 待确认问题

### Q1: 问题描述
- 为什么不确定：
- 当前可选假设：
- 如果假设错误的风险：
- 建议确认人：
- 阻塞级别：Blocking / Non-blocking
```

规则：

- Blocking 问题未确认，不进入实现。
- Non-blocking 问题可以带假设进入实现，但必须在 `notes.md` 或 `log.md` 中记录。
- 人工确认后，必须同步更新 `spec.md` 或 `design.md`。

## Review 门禁

| 门禁                     | 检查内容                  |
| ---------------------- | --------------------- |
| Spec Review            | 功能是否清楚、边界是否完整、验收是否可测试 |
| Design Review          | 方案是否覆盖 Spec，是否引入额外范围  |
| Task Review            | 任务是否原子化，是否每项可验证       |
| Spec Compliance Review | 代码是否逐条满足 Spec         |
| Code Quality Review    | 实现质量、安全、性能、可维护性       |
| Archive Review         | 变更后 Spec、知识库、经验是否同步   |

## 常见陷阱

| 陷阱      | 表现                | 处理方式                         |
| ------- | ----------------- | ---------------------------- |
| 过度规格化   | Spec 写成自然语言伪代码    | 把实现细节移到 design.md            |
| Spec 腐烂 | 代码变了，Spec 没变      | 任何变更都必须同步更新 Spec             |
| 流程官僚化   | 小改动也走完整流程         | 按复杂度分级                       |
| 虚假信心    | 有 Spec 就放松 Review | Spec 替代需求文档，不替代代码审查          |
| 工具复杂性   | 工具链维护成本过高         | 先用 Markdown + 现有 AI Agent 跑通 |

## 与 Harness Engineering 的关系

SDD 是 Harness Engineering 的核心模式之一：

- `constitution.md` 是约束层。
- `spec.md` / `proposal.md` 是需求层。
- `design.md` 是方案层。
- `tasks.md` 是执行调度层。
- Review、测试、归档是反馈和知识沉淀层。

换句话说，SDD 提供 AI 可执行的结构化上下文，Harness Engineering 则提供让这套上下文持续可靠运转的流程、工具、门禁和反馈机制。

## 第一阶段落地建议

1. 先建立 `constitution.md`，只写 10-20 条最重要的项目原则。
2. 为每个新需求创建 `requirements/REQ-xxx/`。
3. 小需求使用 `spec.md + tasks.md`。
4. 中等以上需求使用 `proposal.md + spec.md + design.md + tasks.md`。
5. 每个任务必须有验收标准和验证证据。
6. 合并后必须归档到 `specs/`，并把可复用经验沉淀到 `context/`。
