# Context 目录

`context/` 是 AI 和团队共享的长期上下文。它保存稳定知识、业务程序结构和工程实现物料，不保存一次性讨论。

一个服务从 0 开始时，推荐按下面的顺序建立上下文：

```text
business
  -> domain
  -> architecture
  -> engineering
  -> operations
```

这不是瀑布流程，而是初始化阶段的推导顺序。真实需求开发时，任何一层发现缺口，都可以回写对应目录。

## 建模顺序

### 1. business/

先回答“为什么要有这个服务”。

这里记录业务背景、用户、上下游、价值、服务范围，以及明确不做什么。AI 在进入需求前，应先知道服务面向谁、解决什么问题、外部系统如何协作。

### 2. domain/

再回答“业务世界里有哪些稳定概念和规则”。

这里记录统一语言、核心实体、领域规则、边界条件和例外情况。`domain/` 不关心技术实现，不写 Redis、Kafka、HTTP、数据库表结构，除非它们本身就是业务概念的一部分。

### 3. architecture/

然后回答“这个服务整体如何组织”。

这里记录分层、数据流、运行时结构、依赖边界，以及业务服务的目录蓝图。`architecture/blueprint/` 是业务程序架构的一部分，不属于 `harness/`，因为它直接决定 `src/` 和 `tests/` 如何组织。

### 4. engineering/

再回答“代码应该按什么脚手架落地”。

这里记录代码生成脚手架、模块骨架和可复用实现模式。`engineering/scaffolds/` 是 AI 可以复制改造的工程物料，不是只读示例。

### 5. operations/

同步回答“这个服务如何被构建、验证、部署和观测”。

这里记录构建命令、测试命令、格式化规则、观测指标、故障处理和运行约束。它为 `harness/scripts/verify/` 的项目化提供依据。

## 辅助目录

### decisions/

`decisions/` 放 ADR，用来记录本项目在多个可选方案中做出的重要选择。

一条 ADR 应该说明：

- 当时有什么问题。
- 可选方案有哪些。
- 最终选择了什么。
- 为什么这样选。
- 放弃了什么。
- 后续如果要推翻，需要满足什么条件。

`decisions/` 不是公共知识库。它记录“本项目为什么这样选”，不负责沉淀跨项目通用经验。

### learnings/

`learnings/` 放跨需求、跨项目可复用的经验知识。

如果某条知识来自一次重要决策，可以在 ADR 中记录决策过程，再把可复用结论沉淀为 `learnings/` 下的 TK 条目，或回写到 `architecture/`、`engineering/`、`operations/`。

简单区分：

| 内容 | 应放位置 |
| --- | --- |
| “这次我们为什么选方案 A，而不是 B” | `decisions/` |
| “以后遇到同类问题，应优先考虑方案 A 的条件” | `learnings/` |
| “服务最终采用的分层结构” | `architecture/` |
| “AI 可复制的模块代码脚手架” | `engineering/scaffolds/` |
| “构建、测试、部署、观测规则” | `operations/` |

## 子目录

| 目录 | 内容 |
| --- | --- |
| `business/` | 业务背景、上下游、用户、价值、范围 |
| `domain/` | 统一语言、实体、规则、边界条件 |
| `architecture/` | 分层、数据流、运行时结构、依赖边界 |
| `engineering/` | 代码生成脚手架、模块骨架、工程实现模式 |
| `operations/` | 构建、测试、部署、观测、故障处理 |
| `decisions/` | ADR，记录重要架构决策 |
| `learnings/` | 从真实需求沉淀出来的可复用知识 |

## 写入原则

- 可长期复用才进入 `context/`。
- 每条知识要有适用场景和失效条件。
- 重要知识必须有来源和证据。
- 草稿知识先标 `draft`，被真实需求验证后再升级。
