# 类设计规则

本文件约束同一分层内部的类拆分粒度。`layering-rules.md` 回答"放在哪一层"，本文件回答"同一层内拆多细、哪些类型允许成为 public API"。

## 核心原则

### 1. 业务能力优先一个 public 聚合入口

对一个连续业务流程，优先设计一个 public 聚合入口，让调用方使用业务语言完成一件事。

流程内部步骤可以拆成 private 函数、internal helper 或值对象，但不得让调用方承担固定组合顺序。

### 2. 新增 public 类型必须说明调用方

每个新增 public class / struct / free function 都必须能回答：

- 谁直接调用它。
- 它代表业务概念、外部契约，还是实现步骤。
- 它是否有独立生命周期、独立状态或独立复用场景。
- 不暴露它时，调用方是否仍能完成主要业务用例。

如果没有清晰调用方，优先不要 public 化。

### 3. 抽象有成本，不能默认引入

interface、base class、policy class、strategy class 都会增加理解成本。只有满足以下至少一项时才考虑引入：

- 存在多个真实实现，且调用方需要在运行期或装配期替换。
- 类型隔离外部依赖边界，例如 `ports/`。
- 类型承载稳定业务概念，而不是某个算法步骤。
- 拆分后显著降低主流程复杂度，且不会增加调用方组合负担。

否则优先使用具体类型、普通函数、值对象或 internal helper。

### 4. 组合优先于继承

除非存在清晰的"是一种"关系，且确实需要通过基类多态使用，否则不要引入继承层级。

领域层规则逻辑通常优先使用：

- 值对象表达输入 / 输出。
- 具体聚合入口表达业务能力。
- internal helper 表达局部算法。

### 5. 测试不能倒逼暴露 detail API

不要因为单测方便就把内部步骤暴露为 public 头文件。

优先顺序：

1. 通过 public 聚合入口做行为测试。
2. 对复杂纯算法使用 internal helper，并通过覆盖主入口边界证明行为。
3. 只有当算法本身是可复用业务能力时，才暴露为 public API。

## public / internal 判定表

| 信号 | 倾向 |
| --- | --- |
| 独立业务概念，调用方会直接使用 | public |
| 外部层需要稳定依赖它 | public |
| 有多个真实调用方独立复用 | public |
| 有独立生命周期或独立状态 | public |
| 只是主流程中的算法步骤 | internal helper |
| 只被一个聚合入口调用 | internal helper / private 函数 |
| 调用方必须按固定顺序组合多个 policy | 增加聚合入口，减少 public 步骤类 |
| 只是为了单测方便 | 不应 public 化 |

## Design 必填内容

每个 Design 必须包含类图 / 模块关系图，至少表达：

- public 入口类 / 函数。
- public 值对象。
- internal helper。
- 调用方向。
- 为什么这样拆。
- 为什么不合并。
- 为什么不继续拆。

新增 public 类型超过 3 个时，必须额外说明为什么不提供一个更粗粒度的聚合入口。

如果 Track 修改已有业务源码、public 头文件、构建入口或目录结构，Design / Tasks / Acceptance 必须判断 `context/architecture/implementation-module-map.md` 是否需要同步。

## 评审问题

- 调用方需要理解几个 public 类型才能完成一个用例。
- public 类型数量是否明显多于业务概念数量。
- 是否存在仅为测试暴露的 detail API。
- 类图是否能一眼看出主流程。
- 模块级注释是否说明业务主线，而不只是字段级注释。
- 抽象、继承、策略类是否有真实替换点或复用点。
